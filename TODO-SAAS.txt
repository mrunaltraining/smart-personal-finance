# Master Prompt for Claude - SaaS Transformation Project

## Role and Context
Act as a Principal Software Architect + Senior Full-Stack Engineer + Security Engineer + QA Architect.

**Current State:**
- Existing web application using HTML, CSS, JavaScript, Firebase, GitHub Pages
- Firebase Authentication with email/password and potentially Google login
- Working application functionality and business logic

**Target State:**
- Production-quality, scalable SaaS application
- Support for both Desktop/Web and Mobile/responsive web
- Professional architecture with clear separation: frontend, backend, APIs, business logic, database, authentication, payments, integrations

**Critical Approach:**
Do not blindly rewrite the application. First understand the existing application thoroughly, identify what already works, preserve existing functionality, and then refactor incrementally.

## Phase 1: Audit the Existing Application

Before making any code changes, perform a comprehensive analysis:

### 1.1 Repository Analysis
Analyze the complete repository structure and identify:
- Current frontend architecture and patterns
- JavaScript modules and their responsibilities
- Existing business logic implementation
- Firebase usage patterns and configuration
- Authentication flow implementation
- Firestore/database structure and queries
- Existing API calls and data fetching
- State management approach
- Reusable components and utilities
- Responsive/mobile behavior implementation
- Validation logic and error handling
- Existing test coverage
- Configuration and secrets management

### 1.2 Security Assessment
Identify:
- Code exposing business-critical logic in frontend JavaScript
- Security vulnerabilities (XSS, injection, authentication bypasses)
- Hardcoded secrets or sensitive data
- Insecure data transmission
- Authorization gaps

### 1.3 Code Quality Assessment
Identify:
- Duplicated code patterns
- Tightly coupled modules
- Code that should move from frontend to backend
- Areas requiring unit/integration testing
- Performance bottlenecks
- Accessibility issues
- Mobile/web UI problems

### 1.4 Deliverables
Before implementing major changes, provide:
- Architecture assessment document
- Migration plan with phases
- Risk analysis
- Preservation strategy for existing functionality

**Critical Rule:** Do not remove existing functionality unless there is a strong technical reason.

## Phase 2: Target Architecture

### 2.1 System Architecture
Refactor toward a production SaaS architecture with clear separation of concerns:

```
                    ┌─────────────────────┐
                    │      Browser        │
                    │                     │
                    │ Web / Mobile Web UI │
                    └──────────┬──────────┘
                               │
                         HTTPS / REST
                               │
                               ▼
                    ┌─────────────────────┐
                    │     Backend API     │
                    │                     │
                    │ Authentication      │
                    │ Authorization       │
                    │ Business Logic      │
                    │ Subscription       │
                    │ Referral System     │
                    │ Payment Logic       │
                    │ Validation          │
                    └──────────┬──────────┘
                               │
              ┌────────────────┼────────────────┐
              ▼                ▼                ▼
         Firebase DB      Razorpay          Resend
          / Storage       Payments           Email
```

### 2.2 Security Principle
**Treat the frontend as an untrusted client.**
- Important business logic must reside on the backend
- Authorization, subscription validation, payment verification must be server-side
- Secrets must never be exposed to frontend JavaScript
- All sensitive operations require server-side validation

Implement secure token verification:
```
Browser
   ↓
Firebase Authentication
   ↓
Firebase ID Token
   ↓

   ↓
Go Backend
   ↓
Verify Firebase token
   ↓
Extract UID
   ↓
```

## Phase 8: Subscription Model

### 8.1 Subscription Plans
Implement three subscription tiers:
- **Free:** ₹0
- **Pro Monthly:** ₹99/month
- **Pro Annual:** ₹999/year

### 8.2 Server-Side Pricing Control
Make pricing configuration server-controlled, not client-controlled:
- Use plan identifiers instead of raw amounts
- Backend determines actual pricing for each plan
- Frontend only references plan IDs

### 8.3 Secure Pricing Flow
**Do not trust amounts from the browser:**
```json
// ❌ INSECURE - Never trust this
{
  "amount": 99
}

// ✅ SECURE - Use plan IDs
{
  "plan_id": "pro_monthly"
}
```

The server resolves the actual amount based on the plan_id.

## Phase 9: Subscription State Machine

### 9.1 State Design
Design subscription states carefully with clear transitions:
- **FREE** - No active subscription
- **ACTIVE** - Active paid subscription
- **PENDING** - Payment in progress
- **PAST_DUE** - Payment failed, grace period
- **CANCELLED** - Subscription cancelled
- **EXPIRED** - Subscription period ended
- **PAYMENT_FAILED** - Payment processing failed

### 9.2 State Transitions
Define valid state transitions:
```
FREE
 ↓
PAYMENT_PENDING
 ↓
ACTIVE
 ↓
CANCELLED
 ↓
EXPIRED
```

### 9.3 State Security
Handle payment failure, cancellation, and expiration correctly on the server side.

**Critical Rule:** Never grant premium access merely because the frontend reports successful payment. All state changes must be verified server-side.

### 10.1 Integration Principles
- Integrate Razorpay according to current official Razorpay documentation

- Follow Razorpay's security requirements exactly

### 10.2 Credential Security
**Keep all Razorpay secret credentials on the backend only:**

- Frontend may receive: Public Razorpay key ID (where required by checkout)

### 10.3 Documentation Compliance
Always reference the latest official Razorpay documentation at implementation time. If something depends on specific Razorpay account configuration, explicitly identify it as configuration you must provide.

## Phase 13: Payment Success Verification

### 13.1 Signature Verification
Implement secure payment verification using Razorpay's official signature verification mechanism.

### 13.2 Verification Security
**Never trust payment success from the frontend:**
```javascript
// ❌ INSECURE - Never trust this
payment_success = true
```

### 13.3 Server-Side Verification
The backend must verify:
- razorpay_order_id
- razorpay_payment_id
- razorpay_signature

Against the expected order and authenticated user using Razorpay's official verification method.

### 13.4 State Updates
Only after successful signature verification should the application update subscription/order state.

- Out-of-order event handling

### 14.2 Idempotent Processing
Design webhook processing so the same webhook can safely be delivered multiple times:
```
Webhook
   ↓
Verify Signature
   ↓
Check Event ID
   ↓
Already processed?
   ├── Yes → Return success
   └── No
        ↓
Validate event
        ↓
Update payment/order
        ↓
Update subscription
        ↓
Record event
```

## Phase 44: Domain-Oriented Design

### 44.1 Independence Principle
Keep domain concepts independent from infrastructure:
```
HTTP
 ↓
Handler
 ↓
Application Service
 ↓
Domain Logic
 ↓
Repository Interface
 ↓
Firebase Implementation
```

### 44.2 Interface Abstraction
The domain/service layer should not directly depend on HTTP. The business logic should not know whether the database is Firebase, Supabase, or another provider.

### 44.3 Repository Pattern
Example repository interface:
```go
type SubscriptionRepository interface {
    GetByUserID(ctx context.Context, userID string) (*Subscription, error)
    Save(ctx context.Context, subscription *Subscription) error
}
```

Then provide `FirebaseSubscriptionRepository` behind the interface. This allows the persistence layer to be replaced later without rewriting business logic.

## Phase 46: Interface Design

### 46.1 Strategic Interfaces
Use interfaces where they provide real architectural value. Good candidates:

- ReferralRepository
- Clock

### 46.2 Payment Provider Example
```go
type PaymentProvider interface {
    CreateOrder(ctx context.Context, req CreateOrderRequest) (*Order, error)
    VerifyPayment(req PaymentVerificationRequest) error
    ProcessWebhook(ctx context.Context, payload []byte, signature string) error
    Refund(ctx context.Context, paymentID string, amount int64) error
```

This allows Razorpay to be replaced later without rewriting subscription business logic.

### 46.3 Interface Principle
Do not create interfaces for every trivial struct just to increase abstraction.

## Phase 62: Deployment Versioning

### 62.1 Semantic Versioning
Use Semantic Versioning: `MAJOR.MINOR.PATCH`

Examples:
- `v1.0.0`
- `v1.1.0`
- `v1.1.1`
- `v2.0.0`

### 62.2 Version Interpretation
**MAJOR** - Breaking changes (`v1.x.x → v2.0.0`):
- Breaking API contract
- Incompatible database migration
- Removal of supported functionality
- Major architectural/product change that breaks compatibility

**MINOR** - Backward-compatible features (`v1.1.0 → v1.2.0`):
- New feature
- New API endpoint
- Referral system
- New subscription capability
- New UI functionality

**PATCH** - Backward-compatible fixes (`v1.2.0 → v1.2.1`):
- Bug fixes
- Security fixes
- Minor performance fixes
- Documentation fixes (where appropriate)

## Summary

This master prompt provides a comprehensive framework for transforming an existing web application into a production-quality SaaS platform. The phased approach ensures:

1. **Preservation of existing functionality** through thorough auditing
2. **Security-first design** with proper separation of concerns
3. **Scalable architecture** that can grow with the business

Follow this framework systematically, adapting specific implementations based on the actual existing codebase while maintaining the core principles of security, scalability, and professional software engineering.
